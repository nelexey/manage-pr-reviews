# Сервис назначения ревьюеров для Pull Request’ов

Внутри команды требуется единый микросервис, который автоматически назначает ревьюеров на Pull Request’ы (PR), а также позволяет управлять командами и участниками. Взаимодействие происходит исключительно через HTTP API.

## Стек

Проект реализован с использованием следующих технологий и инструментов:
- **Python 3.12** — основной язык программирования.
- **FastAPI** — веб-фреймворк для построения асинхронного REST API.
- **PostgreSQL** — основная реляционная база данных.
- **SQLAlchemy 2.0** — ORM для работы с базой данных (в асинхронном режиме).
- **asyncpg** — асинхронный драйвер для PostgreSQL.
- **Pydantic V2** — валидация данных и сериализация схем.
- **Alembic** — управление миграциями базы данных.
- **Uvicorn** — ASGI-сервер.
- **Docker & Docker Compose** — контейнеризация приложения и базы данных.
- **Pytest, pytest-asyncio, httpx** — фреймворк для написания и запуска E2E и интеграционных автотестов.
- **Locust** — инструмент для нагрузочного тестирования.
- **Ruff & pre-commit** — линтинг, форматирование кода и проверки перед коммитом.
- **Makefile** — автоматизация рутинных задач (запуск, остановка, просмотр логов).


### Запуск через Makefile
Если у вас установлена утилита `make`, вы можете использовать следующие команды:

Запуск проекта (поднимает базу данных и API в фоновом режиме):
```bash
make up
```

Сборка / пересборка Docker-образов:
```bash
make build
```

Просмотр логов приложения:
```bash
make logs
```

Остановка проекта:
```bash
make down
```

### Запуск через Docker Compose
Если у вас нет `make`, используйте нативные команды Docker:

```bash
docker-compose up -d --build
```
Для остановки контейнеров:
```bash
docker-compose down
```

## Нагрузочное тестирование
Для проверки производительности приложения под высокими нагрузками (в проекте реализована защита `ConcurrencyLimiterMiddleware`), вы можете воспользоваться скриптом наполнения базы данных и инструментом Locust.

Сидирование базы данных (запускается из корня проекта при запущенном Docker):
```bash
python scripts/seed.py
```
Запуск нагрузочного теста (web UI будет доступен на `localhost:8089`):
```bash
locust
```

## Тесты
Проект покрыт интеграционными (End-to-End) тестами, проверяющими полный жизненный цикл данных в реальной базе (через HTTP запросы).

Для запуска тестов (убедитесь, что приложение запущено через Docker):
```bash
pytest tests/test_e2e.py -v
```

## По проекту

По части реализации: для работы с БД я использовал паттерн Репозиторий (слой `methods/`), чтобы отделить SQL-запросы от бизнес-логики. В парадигме ORM это не является строгой необходимостью, но для меня это устоявшаяся лучшая практика (Best Practice), обеспечивающая чистоту кода.

В проекте намеренно опущен слой `services`, а бизнес-логика расположена внутри обработчиков (`web/handlers/`). По-хорошему, её следовало бы вынести в отдельный слой, но в рамках масштаба текущего задания я решил не усложнять архитектуру.

Касательно производительности: сервис держит нагрузку с запасом (порядка 300-500 RPS). Тем не менее, я добавил `ConcurrencyLimiterMiddleware`, который использует семафор на уровне `asyncio`. Это наиболее простой и эффективный способ реализовать Concurrency Limiter, чтобы не допустить открытия слишком большого числа одновременных сессий к базе данных и защитить сервис от падения под экстремальной нагрукой.

Вопросов по ТЗ не возникло. Разве что, вместо случайного выбора двух ревьюеров, на практике было бы логичнее назначать тех участников команды, у которых в данный момент меньше всего задач на ревью. Тем не менее, логика реализована строго по требованиям задания.
